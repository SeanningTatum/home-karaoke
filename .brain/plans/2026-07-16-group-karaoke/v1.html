Group Karaoke Rooms

2026-07-15 · feature: group-karaoke (new, feat-007) · draft · round 0

TL;DR

Build the app's core feature: a host creates a karaoke room and gets a big-screen view (YouTube player + live queue + join QR); guests scan the QR on their phones, pick a nickname, search YouTube, and add songs — no signup. A Durable Object per room holds live state (queue, playback, roster) and syncs everyone over hibernating WebSockets; the host's screen is the only audio output and the host's phone-or-screen controls play/pause/skip/reorder/volume.

Decisions needed

1. How do participants (guests on phones) get an identity?

Hosts are logged-in users (existing Better Auth). Guests scanning a QR at a party must not be forced through email signup. Three ways to give them an identity:

OptionProsCons
Zero-friction join (nickname only); no junk rows in user table or admin dashboard; identity lives as a signed room-scoped token + WS attachment; vanishes when room closes Guests invisible to Better Auth — can't reuse protectedProcedure for guest actions (guest actions flow through the DO/WS anyway); new small token-signing helper to build + test
Real sessions; protectedProcedure works for guests; upgrade path to full account later Every party guest becomes a user row (pollutes admin dashboard + analytics, needs cleanup job); plugin config + schema migration; heavier than the need
No new auth surface at all Party-killer UX — nobody signs up with a mic in their hand; effectively kills the QR-join concept

2. Realtime transport for queue + playback sync?

Queue changes and play/pause must reach the host screen and every phone in <1s to feel live. Research (2026) confirms Cloudflare's documented standard for room-based realtime:

OptionProsCons
Cloudflare's canonical pattern for exactly this; instant bidirectional sync; idle hibernating rooms bill $0 duration (a room open all evening costs ~nothing while idle); strict write ordering per room; DO SQLite holds live state so a redeploy/eviction doesn't wipe the queue Net-new infra for this repo (binding, DO class export, new_sqlite_classes migration, WS client hook) — the plan's biggest single chunk
Zero new infra; reuses existing React Query patterns Play/pause lag feels broken; N phones × poll rate hammers D1; still need somewhere consistent to hold live playback state — ends up needing a DO anyway
Less boilerplate; built-in fan-out helpers Beta (~June 2025), less battle-tested, adds a dependency between us and the primitive; raw DO API is fully documented and stable

3. How do participants search YouTube?

Key constraint: official search costs 100 quota units per call against a 10,000 units/day free quota → ~100 searches/day. A party of 10 people searching freely can burn that in one evening. Requires a Google Cloud API key (server-side only, restricted to YouTube Data API v3).

OptionProsCons
Official, reliable, ToS-clean; debounce (search on submit, not keystroke) + caching identical queries stretches quota; paste-a-YouTube-URL always works as a quota-proof escape hatch; videos.list embeddable pre-check costs only 1 unit Needs you to create a Google Cloud project + API key; hard ~100 searches/day ceiling until a quota increase is granted (slow for hobby projects — design around the default)
No key, no quota ToS violation risk; breaks when YouTube changes markup; Cloudflare edge IPs are exactly what YouTube's anti-bot targets; unfit for a public app
Zero external setup; ships faster Much worse guest UX — searching YouTube on a phone then copying a URL is clunky mid-party; search is half the participant experience

4. Where does live room state live — DO as source of truth, or D1?

OptionProsCons
Queue mutations are zero-latency, strictly ordered, colocated with the broadcast; D1 keeps only what outlives the party (room row, later history); matches Cloudflare's documented split Two storage places to reason about; queue state not visible in Drizzle Studio (acceptable — it's ephemeral by nature)
One database; queue queryable/seedable like other tables Every play/pause/reorder becomes a network round-trip to D1 before broadcast (laggy); write-hot ephemeral data in the durable store; loses DO's ordering guarantee — race-prone under simultaneous adds

  5. Phase 5 — Host controls + polish. Phase 6 — Verify + ship. i18n strings, seed fixtures, feature-verifier browser walk (golden path: create → QR join → search → add → play → reorder → skip; error path: non-embeddable video auto-skips), verification doc, /verify-done, feature_list flip via brain ship. Acceptance: verification doc PASS + harness check green.
Why DO before any UI (phase 2 before 3/4)?

Every screen is a thin view over the DO's broadcast state. Building the player against mock state first would mean rewiring it later; building the socket layer first lets phases 3–5 run partly in parallel across sub-agents against a real contract (the typed WS message schema).

Error paths

FailureDetected byHandled byUser sees

WS drops (phone locks, wifi blip) close/error event in useRoomSocket reconnect with backoff + full state resync from DO on reconnect brief "reconnecting…" pill; queue refreshes itself
Autoplay blocked on auto-advance onAutoplayBlocked event host screen shows resume overlay; one click resumes "Tap to keep the party going" overlay on host screen
Room code invalid / room closed RoomNotFound / RoomClosed from repo or DO tagged error → NOT_FOUND; join page error state "Room not found — check the code" with retry field
DO evicted / redeploy mid-party constructor rehydration path queue + playback state persisted in DO SQLite; sockets rebuilt from serialized attachments nothing — party continues

Testing plan

Open questions

  • Queue fairness: strict FIFO, or round-robin per singer so one enthusiast can't stack 10 songs? (FIFO assumed for MVP.)
  • Room lifetime: auto-close after N hours idle? Persist history ("last night's setlist") to D1 as a later feature?
  • Can participants remove/reorder their OWN queued songs, or is all queue management host-only?
  • Should search bias to karaoke versions (append "karaoke" to queries / videoCategoryId=10), or search raw YouTube?
  • Safari validation: does auto-advance playback survive without a fresh gesture on the actual host device (older smart-TV browsers especially)? Needs an empirical spike in phase 3.
