Karaoke UI/UX Overhaul — strip the boilerplate, make it fun

2026-07-16 · feature: ui-overhaul (to be registered as feat-008) · draft · round 0

TL;DR

Group karaoke (feat-007) shipped, but the app still looks and reads like the Cloudflare SaaS starter it was built on — a marketing landing page for a boilerplate, monochrome ShadCN everywhere, "Acme Inc." in the sidebar. This plan removes every boilerplate surface, replaces the landing/dashboard/auth pages with karaoke-first content, and reskins the host TV screen and guest phone flow with a research-backed "night-club stage" visual identity plus a set of quick UX wins (Jackbox-style join, 10-foot type scale, tap-based reorder, celebration moments).

Context

Per plan 2026-07-16-group-karaoke (reviewed, 1 round), feat-007 shipped through PR #1 and merged to main on 2026-07-16 (last checkpoint: "PR #1 merged… next: prod deploy path"). No feature is currently in-progress, so the one-in-progress policy is clear for this work.

Three research passes feed this plan: a full codebase inventory (boilerplate vs karaoke classification), a Refero visual-reference sweep (Suno, Deezer, Partiful, YouTube Music, Verse, Sora, Stryds), and a web UX sweep (KaraFun/Smule/Singa teardowns, Jackbox/Kahoot join flows, Google TV / tvOS 10-foot guidelines, shared-queue fairness research).

Known conflict: .brain/codebase/design-system.md is titled "Boilerplate Surface" and explicitly forbids gradients, new palette colors, and emoji — the exact opposite of this redesign. It gets rewritten in Phase 1; the old doc described surfaces this plan deletes.

Research digest — what the three passes found (condensed)

Codebase inventory

  • Pure boilerplate: `/` landing (SaaS hero, "what's wired" cards, harness section, quickstart terminal), `/admin/kitchen-sink`, admin analytics demo, file-upload feature, `home.json` + `upload.json` namespaces, "Acme Inc." / "CloudFlare SaaS Starter" brand strings, placeholder github.com/ links.
  • Mixed: dashboard (one karaoke "Host a room" card inside a boilerplate educational grid), auth pages (AuthShell split-pane with "Production-grade auth, batteries included" copy).
  • Karaoke, no personality: `/room/:code` and `/join/:code` are pure monochrome ShadCN — visually identical to the admin pages. Copy in room.json is already fun ("Start the party"); the visual layer is not.

Refero visual research

  • Suno: near-black canvas, warm grainy gradient, pink→yellow gradient pill as the single brightest element. Deezer: single-accent-on-black discipline, oversized display type. Partiful: color as gradient washes, tilted card scatter. Stryds: neon-ring motif — literal "room" framing for the lobby.
  • Player/queue: Deezer's lyric player (one bold active line, rest dimmed) is the closest existing karaoke pattern; YouTube Music's queue rows (thumbnail + meta + drag handle, Up Next as first-class surface) port directly.
  • Join: Sora's dark code-entry modal; nickname editors = one field, live avatar preview, one button. Verse's "Add a song" modal is a near-verbatim template for guest search-and-add.
  • Gap none of the references solve: "added by" attribution on queue rows — home-karaoke originates this (avatar/nickname chip per row).

Web UX research

  • Jackbox: join = ROOM CODE + NAME, nothing else; "illusion of awareness" — the app responds to you. Kahoot: QR joining + random-nickname spinner; too-small TV QR codes are a documented failure mode.
  • KaraFun: users hate fiddly drag-reorder, ask for "move to top" / "move up one" buttons; just shipped Singer Rotation (fairness = people who haven't sung yet, not vote counts).
  • 10-foot UI: nothing under ~24px, bold weights only, 5%+ safe margins (≈48–90px sides), unmistakable focus states.
  • Celebrations: confetti only at rare, earned moments (room live, guest's first song plays) or it numbs fast. State caps explicitly ("2/3 songs queued") — invisible limits read as unfair (Yokee complaint).
  • YouTube-karaoke pain: volume inconsistency between videos + ad gaps — candidate future work, out of scope here except where noted.

Decisions needed

1. Visual direction for the whole app?

All three options come from the Refero pass; sample palettes below are starting tokens, tuned during Phase 1.

OptionProsCons
Reads great in a dark living room; video/thumbnails get the spotlight; matches karaoke-night mood Dark-first means the light theme becomes secondary/deprioritized
Maximum party energy, very distinctive Harsh on a TV in a dark room; harder to keep video legible
Fresh, social-invite feel; great for landing page Light UI glare on a TV at night is actively bad for the core use case

2. How deep does boilerplate removal go?

Everything agrees the marketing landing, kitchen-sink, and SaaS copy go. The question is the admin area and file-upload feature (both shipped features in feature_list.json).

OptionProsCons
User management (ban/roles) stays useful for a real deployment; demo noise gone; feature_list rows flipped to cut honestly Admin area needs a light reskin so it doesn't clash
Smallest surface, purest karaoke app Loses ban/user tooling you may want when rooms go public; more deletion churn
No deletion risk Boilerplate demos remain user-visible; contradicts the ask

3. What does the landing page (`/`) become?

OptionProsCons
Guests who type the URL manually still get a Jackbox-style two-field join; sells the app to visitors; SEO keeps working (locale routes) Most build effort of the three
Fast to build, zero fluff Wastes the first impression; no explanation for new visitors
Fewest hops for the dominant user (guests) Confusing for first-time hosts; no room to explain the product

4. UX scope: reskin only, or include the research quick wins?

Quick wins = nickname random-spinner, tap-based "move up / move to top" reorder buttons (alongside existing drag), lobby "everybody's in" joined-guest moments on the TV, "added by" avatar chips on queue rows, per-guest "you're up in ~N songs" indicator, celebration moments (room live, guest's first song). Heavy items = KaraFun-style singer rotation algorithm, audio volume normalization.

OptionProsCons
Delivers the "fun" ask, all client/DO-light changes, no queue-ordering semantics change Fairness rotation deferred to a future feature
Lowest risk, fastest App looks fun but joins/queueing still feel utilitarian
Fixes the top complaints in the category in one pass Rotation changes DO queue semantics (needs its own design + tests); audio normalization is hard against YouTube embeds — high risk of scope blowup

5. Typography: bring in a display font?

Research direction: one flashy display face for hero moments only (room title, "Now Singing", big numbers), Inter stays the workhorse. Fonts must be self-hosted (Workers, no runtime Google Fonts dependency).

OptionProsCons
Instant personality where it counts; small woff2 subset (~30-60KB) License check + font files in repo; tiny page-weight cost
Zero new assets Still reads "SaaS"; hero moments stay generic
