## Findings for main thread

1. **The embeddability pre-check works, and a real search for "dancing queen" surfaces at least one non-embeddable result.** The literal top hit for this query (`"ABBA - Dancing Queen (Karaoke Version)"` by "Sing King") has embedding disabled by its uploader. `resolveVideo` correctly returns `VideoNotEmbeddableError` (400) for it rather than queuing a video that would fail in the player later — this is the feature working as designed, confirmed against the real YouTube Data API for the first time (previously only unit-testable). Not a bug; noting it because it means a real user's very first "Add" click on this popular query has roughly even odds of needing a second try, which might be worth a "try another result" hint in the toast copy — a UX polish suggestion, not a defect.
2. **`SearchTab` unmounts when its `/join/:code` tab loses focus (Radix Tabs' default lazy-unmount), which discards the in-memory search-result list.** Switching from Queue back to Search after `onQueued` auto-switches away shows a completely blank search form — not merely a hidden one — so a guest who wants to add a second song from the *same* search must retype and resubmit the query (confirmed: a resubmission of the identical query now also risks an immediate cache hit that returns only the single video already picked, not the original 12-result list). This script sidestepped it by using paste-link for the second add rather than fighting the remount. Worth a look: either persist search state at the route level (lift the mutation above the tab, or use Radix's `forceMount` + CSS hide) if "add multiple songs per visit to Search" is an intended guest flow — currently each visit to the Search tab starts from zero.
3. **Playback actually played in this run** — unlike the two prior golden-path walks (`2026-07-16.md`, `2026-07-16-controls.md`), which both hit either a real headless-Chromium `onError` or a documented "can't verify audio" limitation, this run's "Start the party" click produced a genuinely progressing embed (`0:00 → advancing`, Pause icon shown, no autoplay-blocked overlay). Environment-dependent, not something the app controls either way — noted for completeness, not actionable.
4. **`NowSingingBanner`'s title + "sung by {name}" render as adjacent JSX children with only a CSS flex `gap` between them** (`app/components/room/now-singing-banner.tsx`) — visually fine (confirmed in the screenshots: there's a clear gap on screen), but a script reading `.textContent()` sees them concatenated with no whitespace (`"…(HD Karaoke)sung by SearchTester"`). Purely a test-tooling observation, not a UI bug — flagging only so a future `e2e/*.spec.ts` assertion on that text doesn't get tripped up by it.
5. **No missing `data-testid`s** were hit for anything this walk reached — same full set as the predecessor's list, all resolved correctly, including `room-play-pause-button` gating a queue promotion before `room-start-party-button` could load real video (matches app logic: the player only cues/plays `playback.currentItem`, which the play/pause transport control populates from the queue head).
6. **This walk also incidentally confirms fix `5224bc6` didn't need to activate** — since the key is now valid, every `getVideo`/`resolveVideo` call this run took the keyed `videos.list` path directly (no oEmbed fallback was exercised); the fallback's own unit coverage (`app/services/__tests__/youtube.test.ts`) remains the source of truth that the degrade-on-failure logic itself works, this walk only confirms the *valid-key* happy path end-to-end.
