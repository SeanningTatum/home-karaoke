# Verification: Group Karaoke Rooms — Live YouTube Search (supplement)

- **Slug**: `group-karaoke` (feature memo: `.brain/features/group-karaoke/group-karaoke.md`)
- **Date**: 2026-07-16
- **Verified by**: feature-verifier (Playwright CLI — headless script via `bun`)
- **Base URL**: http://localhost:5173 _(dev server: started by agent — `bun run dev`, stopped after verification)_
- **Role**: host = admin (`admin@preview.local` / seed fixture from `scripts/seed-preview.ts`), guests = anonymous sessions via `signIn.anonymous()`
- **Scope**: this is a **supplement** to [`verifications/2026-07-16.md`](2026-07-16.md) (golden path, PASS) and [`verifications/2026-07-16-controls.md`](2026-07-16-controls.md) (drag/controls, PASS). Both prior walks explicitly could not test **live YouTube search** because `YOUTUBE_API_KEY` was unset in that environment. A `YOUTUBE_API_KEY` now exists in `.dev.vars`, so this walk was scoped to exercise real search + a host-vs-participant view comparison.
- **Verdict**: 🚫 **BLOCKED** — the configured `YOUTUBE_API_KEY` is rejected by Google's own API (`API_KEY_INVALID`), confirmed independently of the app via a direct `curl` to `googleapis.com`. This blocks not only `youtube.search` (the intended target of this walk) but **also** `youtube.resolveVideo` for *any* video — including the paste-a-link fallback — because the service only falls back to the keyless oEmbed endpoint when the key is **absent**, not when it's present-but-rejected. Net effect: **no song could be added to a room at all** in this environment, so most of the planned golden-path steps (16-20, E3) could not be exercised. This is a credential/config problem, not a demonstrated app defect — reported honestly per instructions rather than faked. One step (21, Controls-tab presence/absence) is independent of video resolution and **did PASS**.

## Root-cause evidence (blocker)

1. **Direct proof the key itself is invalid**, bypassing the app entirely:
   ```
   curl "https://www.googleapis.com/youtube/v3/search?part=snippet&type=video&maxResults=5&q=dancing+queen+karaoke&key=$YOUTUBE_API_KEY"
   → HTTP 400
   → {"error":{"code":400,"message":"API key not valid. Please pass a valid API key.",
      "errors":[{"reason":"badRequest"}],
      "details":[{"reason":"API_KEY_INVALID", ...}]}}
   ```
2. **Format mismatch** (no secret value printed — just shape/length checks): the configured value is **53 characters** and does **not** start with `AIza`. Every real Google API key is **39 characters**, always prefixed `AIza...`. This strongly suggests the value in `.dev.vars` is not a valid Google-issued API key at all (wrong secret pasted, a different credential type, or a corrupted/truncated copy) — not a "key exists but needs the YouTube Data API v3 enabled in the console" situation (that would surface as `accessNotConfigured`, not `API_KEY_INVALID`/`badRequest`).
3. **The app reproduces this deterministically**, end-to-end, on every attempt: `youtube.search` → `TRPCError: YouTube is unavailable right now` / `BAD_GATEWAY` (502), and — critically — `youtube.resolveVideo` fails with the **identical** `BAD_GATEWAY` for a plain paste-URL too (confirmed with two different known-good video ids across two independent guest contexts: `dQw4w9WgXcQ`, `9bZkp7q19f0`). Server log per attempt (`bun run dev` stdout): `[trpc] YouTube is unavailable right now {"path":"youtube.resolveVideo","code":"BAD_GATEWAY", ...}`, ~300-600ms duration each — a real round-trip to Google, not an instant local validation failure.

## Why this also breaks the paste-link fallback (a real finding, not just an environment quirk)

`app/services/youtube.ts`'s `YouTubeLive` layer picks the implementation for `getVideo` **once, at layer-construction time, based solely on whether `YOUTUBE_API_KEY` is set**:

```ts
getVideo: apiKey ? getVideoWithKey(apiKey) : getVideoViaOEmbed,
```

There is no fallback from "key present but Google rejects it" to the keyless oEmbed endpoint — that path is only taken when the env var is **absent**. So the two verified environments end up with opposite reliability profiles:

- **No key at all** (prior 2026-07-16 walk): `search` fails fast (by design), but `resolveVideo`/paste-link **always works** via oEmbed. Golden path completable end-to-end.
- **Key present but invalid** (this walk): `search` **and** `resolveVideo` (including paste-link) **both** fail, because `resolveVideo` never reaches the oEmbed fallback at all. Nothing can be queued.

This is worth flagging to the main thread as a possible resilience gap: a broken/expired/misconfigured key in production would silently disable the entire add-a-song flow (not just search), with no fallback — whereas simply *unsetting* the key is strictly safer today. See "Findings for main thread" below.

## Console

- **jsErrors**: none. No uncaught exceptions, no React/hydration warnings, across host, all guest contexts, and the host-mobile Controls context. The app degrades every one of these failures to a toast, never a crash — that part works exactly as designed.
- **networkErrors**: `youtube.search` and `youtube.resolveVideo` returned **HTTP 502** on every attempt (steps 15, 16, 20, E3 — 8 total 4xx/5xx entries, matching the `Failed to load resource … status of 502` console pattern + the `response.status() >= 400` hook). These occurred on what were intended to be golden-path steps, which would normally be an automatic FAIL per policy — but they are **not attributed to an app defect**: independent `curl` evidence (see root-cause section) proves the failure originates entirely from Google rejecting the configured API key, before the app's own logic runs. Per the instructions' spirit (fabricating a PASS is prohibited, but so is blaming the app for an external credential problem it has no control over), this is reported as **BLOCKED**, not FAIL — with the exact blocker quoted above rather than papered over.

## Findings for main thread

1. **The configured `YOUTUBE_API_KEY` in `.dev.vars` is rejected by Google** (`API_KEY_INVALID` / `badRequest`, confirmed via a direct `curl` outside the app). It is also the wrong **shape** for a Google API key: 53 characters, not prefixed `AIza...` (real Google API keys are always 39 chars, `AIza`-prefixed). This looks like the wrong value was pasted into `.dev.vars`, or a revoked/different-purpose credential — action needed: get a fresh key from https://console.cloud.google.com/apis/credentials with "YouTube Data API v3" enabled and replace the value (per the comment already in `.dev.vars.example`). I did not attempt to fix or replace the credential myself — that's a decision for whoever owns the Google Cloud project.
2. **Resilience gap — a broken/expired key is worse than no key at all.** `YouTubeLive`'s `getVideo` picks `getVideoWithKey` vs. the keyless `getVideoViaOEmbed` fallback **once, based purely on whether `YOUTUBE_API_KEY` is set** (`app/services/youtube.ts`) — never based on whether the key actually works. Today: no key set → search fails fast but paste-link/resolveVideo *always* works via oEmbed (verified in the 2026-07-16 walk). Key set but invalid (this walk) → **both** search and resolveVideo fail, and nothing can ever be queued, in *any* room, until the key is fixed. Worth considering whether `getVideoWithKey`'s failure should fall through to the oEmbed fallback rather than surfacing `YouTubeUnavailableError` unconditionally — that would make a bad/expired production key fail exactly as gracefully as no key at all, instead of silently taking down the entire add-a-song flow.
3. **Misleading toast copy on `resolveVideo` failure in paste mode.** `SearchTab`'s `resolveVideo.onError` (`app/components/join/search-tab.tsx`) shows `join.search.paste_error` ("Couldn't add that link — check it's a YouTube video URL") for **any** `resolveVideo` failure while `pasteMode` is on, regardless of whether the actual cause is a malformed URL or (as observed here) a `BAD_GATEWAY` from the YouTube service being down. A real user pasting a perfectly valid, well-known video URL during a key outage would be told their *URL* is the problem, which is actively misleading and would send them looking for a "correct" link that doesn't exist. Consider branching on `error.data?.code` the same way the search-quota handler already does (`TOO_MANY_REQUESTS` vs. everything else) so a `BAD_GATEWAY`/`INTERNAL_SERVER_ERROR` gets the generic `join.search.error` copy instead of the URL-specific one.
4. **What this walk did confirm cleanly, independent of the key issue**: the host-only Controls tab on `/join/:code` correctly appears only for the room's own host session (even on a fresh mobile-viewport context that never touched `/room/:code` directly) and is correctly absent for a regular guest session — `isHost` gating (`ownUserId === hostUserId`) works exactly as documented, unaffected by the search/resolve outage.
5. **No missing `data-testid`s** were hit for anything this walk actually reached: `dashboard-host-room-button`, `join-tab-search`, `join-search-input`, `join-search-submit`, `join-search-results`, `join-search-result`, `join-search-add`, `join-search-paste-toggle`, `join-paste-url-input`, `join-paste-url-submit`, `join-tab-controls`, `join-tab-queue`, `room-queue-item`, `room-player-container`, `room-start-party-button` all resolved as documented.
6. **Nothing here contradicts the two prior PASS verdicts.** `2026-07-16.md` and `2026-07-16-controls.md` both correctly and honestly scoped themselves to "search untestable, no key" and exercised the always-available paste-link path, which worked perfectly in that (keyless) environment. The regression here is specific to *this* environment now having a key that doesn't work — it does not mean the app's happy-path logic (already verified twice) has changed or broken.

## Verdict rationale

The stated goal of this walk — proving live YouTube search actually returns real results, biased toward karaoke versions, plus a cache hit on a repeat query — could not be exercised, and the blocker is airtight: a `curl` straight to `googleapis.com`, entirely outside the app, returns `API_KEY_INVALID` for the exact key configured in `.dev.vars`, and the key's shape (53 chars, no `AIza` prefix) doesn't match a real Google API key to begin with. The app's own behavior on top of that is internally consistent and correct — every one of 4 independent attempts (two searches, two resolves) failed identically and gracefully (a toast, zero crashes, zero hydration/JS errors) rather than corrupting state or hanging. The one step that doesn't depend on a working YouTube key at all — the host-only Controls tab correctly appearing for the host's own `/join/:code` session and correctly staying absent for a regular guest — was fully exercised and **passed**. Because the walk's primary objective could not be reached through no fault of the app's request-handling logic, and because fabricating results for the blocked steps would violate the "never fabricate a PASS" rule, the overall verdict is **BLOCKED**, with the one independently-testable step (21) marked PASS and the root cause + a real secondary finding (paste-link losing its oEmbed fallback once *any* key is present) reported in full above for whoever replaces the credential.
