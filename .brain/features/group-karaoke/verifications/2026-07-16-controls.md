## Findings for main thread

1. **Hydration race in the nickname form — script-only footgun, not a product bug.** `NicknameForm`'s input is SSR-rendered then hydrates client-side; a `fill()` issued in the narrow window before React attaches its controlled-input handlers gets silently wiped back to `""` once hydration completes (confirmed via a throwaway repro: `fill()` → wait → `inputValue()` read back empty, with the visible Effect Schema validation error "Expected a string at least 1 character(s) long, actual \"\""). This only bites a scripted browser automating faster than a human ever could — no console error/warning is emitted, and a real user typing has no way to race hydration this tightly. Worked around in this script by re-filling in a poll loop until the value sticks. Flagging in case a future e2e spec (`e2e/*.spec.ts`) hits the same flake on this form.
2. **No missing `data-testid`s.** Every selector needed for this walk resolved as documented in the feature's Key Files: `room-queue-item`, `room-queue-drag-handle`, `room-queue-remove`, `room-queue-own-marker`, `join-tab-controls`, `join-controls-tab`, `room-volume-slider`, `room-guest-reorder-switch`, `room-play-pause-button`, `room-skip-button`.
3. **No roster/participant UI exists** (see E2 above) — not a defect, just an unbuilt affordance; noting it here in case the feature doc's "Dependencies"/"Key Files" list is ever expected to include one.
4. **`HostControls` (used on `/room/:code`) intentionally has no volume/guest-reorder controls** — those live only on the Controls tab of `/join/:code` (host-only, gated by `ownUserId === hostUserId`). This matches the feature doc's "Host-only mutations" description exactly; noting it only because a naive reading of "host screen controls" could expect the volume slider/toggle on `/room/:code` itself, and it is deliberately not there.
