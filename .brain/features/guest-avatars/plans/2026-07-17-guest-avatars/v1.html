Guest Avatars — profile photos in the lobby & room

2026-07-17 · feature: guest-avatars (feat-011) · draft · round 0

TL;DR

Guests get an optional "add a photo" step next to the nickname form on /join/:code; the photo is stored in R2 and their face replaces the gradient-initials avatar everywhere their identity already shows — the TV lobby roster, the compact participants strip, queue rows, the lobby queue summary, and the "You're up!" overlay. The R2 plumbing (binding, service, repository, tagged errors) survived the feat-003 cut, so this is mostly a route + wire-protocol + UI-threading feature, not new infrastructure.

feat-007 group-karaoke shipped 2026-07-16 (plan plans/group-karaoke.html); feat-009 tv-beta-polish merged as PR #6 earlier today — the TV lobby now has a horizontal roster of gradient InitialsAvatar chips, which is exactly where faces belong. feat-003 file-upload was cut by feat-008 (ui-overhaul) but only above the repository layer: the BUCKET R2 binding, Bucket service, BucketRepository (upload/get/remove/list), its 7 tagged errors and unit tests all remain live in app/runtime.ts. The Better Auth user.image column exists with no write path. feat-011 was registered in-progress today (checkpoint 2026-07-17, run note .brain/runs/2026-07-17-guest-avatars.md); two recon passes mapped the upload infra and the full identity path (nickname → WS header → Durable Object roster → UI), and an architecture pass produced the blueprint this plan reflects.

Decisions needed

1. R2 key scheme & cache strategy

How we name the stored object determines cache behavior and cleanup burden.

OptionProsCons
Re-upload overwrites atomically — zero orphans, no cleanup code; versioned URL is unique content so serving can be immutable, 1-year cache Raw URL without ?v= can serve a stale cached image (never emitted by the app)
Every key is immutable content by construction More code; best-effort delete races leave orphaned objects in R2

2. Who writes user.image?

The serving URL must land on the Better Auth user row so the WS route can forward it.

OptionProsCons
Atomic with the R2 put in one Effect program; URL derived from the authenticated session.user.id — a guest can only ever overwrite their own row; no reliance on Better Auth's client field allowlist One new repository method (+ unit test)
No repo change Second round-trip; trusts client-supplied URL string; subject to Better Auth's updateUser field policy

3. Client-side downscale before upload?

Phone photos are routinely 3–10 MB; avatars render at most 80px on the TV.

OptionProsCons
Fast uploads on party wi-fi; tiny R2 storage; crop math is a pure unit-tested helper A thin untestable canvas wrapper (jsdom can't run canvas — kept deliberately thin)
Less client code Most phone photos exceed 2 MB → uploads rejected, bad UX wall

4. Changing your photo mid-room

Avatar is captured into roster/queue entries at WS-connect / queue-add time.

OptionProsCons
No new WS message or re-broadcast path; keeps the diff focused A guest who joins photo-less stays initials-only until they rejoin
Nicer for photo-shy latecomers New protocol message, new reducer, wider test surface — scope growth

5. Photo picker style on the phone

OptionProsCons
Guest picks a flattering photo or snaps one; standard behavior One extra tap vs. camera-direct
Fastest path to a real face at the party No gallery option on most Android pickers; awkward on desktop

Plan of record

  1. Phase 1 — server data plane. Add avatar fields to the wire schemas (QueueItem.singerAvatarUrl, RosterEntry.avatarUrl — optional-with-null-default so old hibernated DO state and old clients decode cleanly), thread avatarUrl through room-state reducers, the DO SessionAttachment, and the WS upgrade route's x-avatar-url header (from session.user.image); new pure helpers app/lib/avatar.ts (key/URL/type/size) + UserRepository.setUserImage. Acceptance: typecheck green; new unit tests for helpers, reducers, schema decode (field present / null / absent), and the repo method all pass.
  2. Phase 2 — upload & serve routes. POST /api/avatar (multipart action: session-gated, type/size validated, BucketRepository.upload to the stable key, setUserImage with the versioned URL) and GET /api/avatar/:userId (streams R2 body, immutable Cache-Control, ETag, 404 on missing) — both following the non-tRPC Effect route pattern; registered in app/routes.ts. No new tagged errors — reuse the 7 mapped bucket errors + ValidationError/UpdateError. Acceptance: typecheck + build green; manual curl round-trip works in dev.
  3. Phase 3 — client capture UI. Photo picker + preview in the nickname form (tap the avatar preview → file input → downscale to 512px square → object-URL preview → upload after session exists, best-effort with inline error and join never blocked); pure computeCoverCrop helper + test; InitialsAvatar gains an optional src prop (AvatarImage with automatic fallback to gradient initials); en+zh i18n keys in the existing room namespace. Acceptance: unit tests green; guest can join with or without a photo.
  4. Phase 4 — wire the five display surfaces. Pass avatar URLs into RosterStrip (lobby + compact), the queue rail singer chips, the lobby queue summary, and the now-up overlay (singer prop extended to carry avatarUrl). Acceptance: typecheck green; photo guests show faces, photo-less guests keep gradient initials everywhere.
  5. Phase 5 — verify & ship. effect-ts-enforcer sweep, full verify-done (typecheck/tests/e2e smoke/build), feature-verifier browser walk (upload a real image on /join, confirm face in lobby roster + compact strip + queue rail + lobby summary + now-up overlay, plus initials fallback for a photo-less guest), update feature memo + CHANGELOG, flip feat-011 via brain ship. Acceptance: verification doc PASS with screenshots.

Error paths

FailureDetected byHandled byUser sees
Wrong file type / over 2 MB server validation (also filtered client-side by accept + downscale) BucketValidationError → 400 inline "Use a JPG, PNG, or WebP" / "too large" under the picker; join still works
Upload fails (R2 error, network) BucketUploadError / fetch rejection best-effort: error shown, join proceeds photo-less "Couldn't upload your photo — you can still join"
Avatar GET for a user with no photo BucketNotFoundError on R2 get 404 response; Radix Avatar auto-falls-back gradient initials chip (today's behavior)
Old hibernated DO state / old clients (no avatar fields) schema decode of stored/wire data optional-with-default fields decode absent → null; SessionAttachment guard unchanged initials fallback — no crash, no disconnect
user.image write fails after successful R2 put UpdateError from setUserImage 500 from action; object remains at stable key (next upload overwrites) upload error message; can retry; join unaffected
