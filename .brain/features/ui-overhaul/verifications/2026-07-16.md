## Additional check (mid-task request)

The user asked, mid-verification, to confirm whether ending a room is reflected to connected guests. This is **not** part of feat-008's original scope but was checked empirically since it's guest/host UX-adjacent and the tooling was already live:

| # | Step | Expected | Observed | Screenshot | Result |
|---|------|----------|----------|------------|--------|
| 12 | Host clicks "End party" → confirms, while a guest is still connected and mid-song | Guest sees the room end **without a manual refresh** | Host correctly navigated to `/dashboard`. Guest's **already-open** tab, given 3s to react, still showed the live `join-tabs` UI (Search/Queue/Controls) with no closed-state banner — **the close did not reach the connected guest over the room WebSocket**. After a **manual reload**, the guest correctly saw the friendly "This room has closed" state (loader-driven, reads the now-updated D1 row) | [`12-guest-live-after-host-ends-room.png`](../screenshots/12-guest-live-after-host-ends-room.png), [`13-guest-reload-after-host-ends-room.png`](../screenshots/13-guest-reload-after-host-ends-room.png) | ❌ (gap, not a crash) |

Root cause (read, not modified): `app/trpc/routes/room.ts`'s `close` mutation only calls `RoomRepository.closeRoom` (a D1 `UPDATE ... SET status = 'closed'`) — it never notifies the room's Durable Object (`app/durable-objects/karaoke-room.ts`) to broadcast a "room closed" message over the live socket or force-close guest connections. The DO already has a analogous idle-timeout closing path (`karaoke-room.ts` ~line 312) that marks the D1 row closed but likewise doesn't appear to broadcast to open sockets either. This is a real live-UX gap, not a data-integrity issue (guests are never shown stale/wrong data — just stale-until-refresh).

## Findings for main thread

1. **TV host play button is unreachable from a cold lobby (real bug, not just a test workaround).** In `app/routes/room/$code.tsx`, `HostControls` (the play/pause button, `room-play-pause-button`) lives inside the same grid wrapper that gets `hidden` (Tailwind, `display:none`) whenever `!hasCurrentItem`. Since `hasCurrentItem` only becomes true *after* a `playback.play` message advances the queue, and the only way to send that message on the TV screen is via the very button that's hidden until `hasCurrentItem` is already true, **the TV screen alone has no way to start a party** once songs are queued in the lobby state. The lobby view (`room-lobby`) also never shows the queue at all — `QueueRail` is nested in that same hidden grid. The only working path (used here) is the host opening their own `/join/:code` → Controls tab, which has an unconditionally-visible `HostControls`. Recommend either: (a) surface a play/start affordance directly in the lobby view once `queue.length > 0`, or (b) show `QueueRail` in the lobby state so the host can at least see what's queued before starting.

2. **Ending a room does not reach connected guests live** (see "Additional check" above) — `room.close` never broadcasts to the Durable Object / open guest sockets. Guests keep interacting with a room that's already closed server-side (queue add/reorder would presumably 40x or silently no-op against a defunct DO/session) until they refresh. Recommend the `close` mutation (or the repo call it wraps) notify the room's DO to broadcast a `room.closed` server message and/or force-close open WebSocket connections, mirroring the existing idle-timeout closing path.

3. **TV lobby uses `overflow-y-auto` (`app/routes/room/$code.tsx` ~line 480), which permits scrolling** if the roster (or, once queue is visible per Finding 1, the queue) grows past the viewport — this contradicts a "must always fit, never scroll" TV requirement raised mid-task. Not reproduced at the guest counts exercised here (a single guest; page `scrollHeight` exactly equalled `innerHeight`, no scrollbar), but the CSS as written does not guarantee it holds at higher counts. Recommend capping/wrapping the roster (e.g. "+N more" past some count) or auditing the TV screen's real height budget so scrolling is structurally impossible rather than just currently avoided.

4. `SearchTab`'s local `pasteMode` state does not reliably reset across a tab-away-and-back (Radix keeps `TabsContent` mounted in some renders and remounts it in others) — this only affected the verification script's robustness (had to poll for the actual DOM state rather than assume one Radix mounting behavior), not a user-facing defect worth its own finding, but worth knowing if a future test relies on that toggle staying in a fixed state across tab switches.

5. No missing `data-testid`s blocked verification — every interactive element referenced in the task brief already had one.

## Verdict rationale

All 11 golden-path steps and both assigned error-path steps passed against the running dev server, across TV (1920×1080) and phone (390×844) viewports, using real host + guest sessions and the documented paste-URL fallback (no `YOUTUBE_API_KEY` locally, as expected). Tap-based queue reorder — the explicit target per the task brief — worked correctly and was confirmed on both the phone and TV screens. The only console errors were a hydration warning attributable to the browser/automation environment (not present anywhere in app code, per the verification policy's exception), and there were zero 4xx/5xx network errors. The mid-task additional check (room-close→guest propagation) is a real gap but is a **live-UX gap, not a crash or data-integrity defect**, and was explicitly requested as an extra check outside feat-008's assigned golden/error paths — it does not change the PASS verdict for the assigned scope, but is flagged prominently above for follow-up, alongside the TV-lobby-can't-start-playback and TV-scroll-containment findings.
